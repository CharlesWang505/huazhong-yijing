## 故障及改进

### 1. 游戏窗口被错归为启动器

现象：游戏明明运行，工具却不断拒绝窗口。原会话已经识别出游戏本体是 `com.bilibili.nslg.exe`，仍拿 `NSLG.exe` 的绑定请求；用户指出这一点。续接时又采用了 `get_window_state()` 返回的错误 `window`，重现相同失败。

证据：A:193 用户指出路径，A:218 至 A:268 恢复观察和游戏操作；B:386、B:406、B:469 恢复同样做法并成功打出一手。

判断与处理：启动器路径和游戏进程路径不同，返回状态又会回写错误归属。保留经过实际成功调用验证的 `actualWindow`，让观察、激活、点击使用一致绑定。

改进：交接记录应把“不要直接改用 state.window”和已验证绑定写在醒目位置。后续故障先对照先前成功调用的参数，避免只重复重置会话或重启程序。

### 2. 手牌遮挡，手工试算及试点过多

现象：牌名在底边或重叠处看不全；反复选牌、截图、粗估，再撤销改选，交互次数多，且有些推断被预览推翻。第一关一手粗估 33，实际 53；误以为的兵种 / 品质数量也多次修正。

证据：A:596；A:1281 用户要求先确认前后几张牌、录入已有游戏工具；A:1289 确认后续应完整识别后用工具算。

判断与处理：把识别、计算和执行分开。先取得完整 8 张牌及状态；离线枚举最多六张的组合；再只执行选定组合并核对预览。

改进：算分脚本直接返回位置和加分明细。减少无效试点，不删去电脑技能要求的每次输入后观察。

### 3. 前期低估弃牌价值，导致出牌次数紧张

现象：前期弱手照常出，后面需要用很少出牌补大量伤害，弃牌次数却还较多。第二关剩 169、3 次出牌时，42 分的组合不足以形成宽裕局面。

证据：A:1183 改为保留五张红橙、弃三蓝；B:1087 至 B:1179 在第三关比较换牌后得到 81 分并与游戏一致。

判断与处理：弃牌有独立资源，保留重复牌、三红核心、君主联动等高收益组件，换散牌以提高每次出牌收益。普通关保留出牌次数还可增加墨卷。

改进：不能永久套用“弃蓝”，后期蓝海、族兵、低星、阶梯和四兵使蓝牌角色改变。每次购买后重新评估。

### 4. 辅助工具并非真实规则的完整实现

现象和证据：第八关首手旧算分 223、游戏 183（B:2843、B:2876），相差两组点将成阵各 20；最终关又校准了稀有共鸣。点名追击在隔了一手未触发同名后仍出现，要求保留跨手状态。

判断与处理：将差值拆成触发项，修正三张点将门槛、追击资格的保留、稀有共鸣的基础品质计数，再重新计算候选。

改进：本次游戏过程中只在内存中修补旧 HTML 的计算函数，**原 HTML 文件没有因此修好**。本技能附带独立实现和回归用例，避免下次又从旧版本开始。

### 5. 用户输入与动画导致状态过期

现象：多次出现 `user input was detected`，中断点可能卡在选牌或提交前；出牌动画中的分数尚未稳定。

判断与处理：重新观察以确认动作是否成功，再决定下一步；依据稳定血量 / 新手牌 / 地图记账。

改进：交接记录写清“已选择什么、刚执行什么、是否已提交”，截图 ID 恢复时重新获取。不要把“准备出牌”误写成“已经造成伤害”。

### 6. 旧对话压缩后的模型请求持续失败

现象：原先能正常回答，自动压缩后连续报错。原会话 A:1302 为压缩记录，A:1308 附加 `goal_objective` 工具结果缺少 `call_id`，A:1310 为拒绝请求：

```text
function_call_output requires call_id on HTTP requests; continuation via previous_response_id is only supported on Responses WebSocket v2
```

判断：这是模型请求续接故障，和游戏窗口归属错误属于不同层面。日志支持“压缩后续接记录缺少调用配对信息”，不能证明哪个组件负全部责任。

处理及局限：本次未找到可可靠配对的 `call_id`，未修改旧会话。通过新会话读取已确认状态、刷新实际游戏画面，继续完成任务。旧线程自身没有验证修复。

改进：分别报告“任务已恢复”和“旧会话已修复”。保存短交接状态，避免把继续按钮当成请求格式修复手段；诊断要按 JSONL 结构提取，控制输出长度。

### 7. 恢复后容易重复诊断，进度反馈不足

现象：用户多次问“卡了吗”；长记录恢复时曾重新回答旧诊断问题，导致游戏推进被打断。

判断与处理：先辨别最新消息是状态询问、暂停还是任务切换。状态询问简短回答后继续原目标；复盘请求则切换为整理，不继续点游戏。

改进：交接状态写明当前模式、最近进展、唯一下一步和已解决问题；约每 30 至 60 秒报告实际进度或新发现，避免仅重复计划。

### 8. 到分不等于本轮已结算

现象：最后一关叫“无尽”，第四手已到 869，超过 800 分，但还剩两次出牌。

判断与处理：按本次界面完成六手，最后核对 9/9、已通关、1267 最高分和奖励勾选。没有在前八关完成或初次过 800 时停止。

改进：把最终可见结果作为完成证据，不能以计算器预测代替。

### 9. 用户补充：游戏启动提权的处理办法

用户提供：为当前 Windows 账户下 `NSLG.exe` 的实际完整路径设置 `REG_SZ` 值 `~ RUNASINVOKER`，位置在 `HKCU\Software\Microsoft\Windows NT\CurrentVersion\AppCompatFlags\Layers`；需要撤销时删除该路径对应的值。该设置不随游戏文件复制，换电脑、账户或路径后重新配置。

处理说明：[操作与续接](operations-and-recovery.md) 的“启动权限与 RUNASINVOKER”保留查询、设置、验证、撤销及旧兼容性标志的处理步骤。它与第 1 项的窗口绑定错配分别排查，也不能修复第 6 项的旧对话请求错误。

证据边界：此方法来自用户后续补充，前两次实战没有可据以确认其效果的运行记录；本次更新没有执行注册表命令。记录为用户提供的解决办法，不把它写成两次通关过程中已独立验证的操作。

## 适合复用的选择逻辑

早期买双壁是因为牌库重复牌多，降低触发门槛能稳定提高收益；后来补刘备同时服务于重复牌、红品质、王者和盾兵联动。购买四红后，弃牌优先寻找第三红；蓝牌增益和四兵加入后，又开始保留能完成品质 / 兵种门槛的蓝牌。

中后期优先取得首手精算奖励，并把保留下来的出牌次数转化为墨卷，形成更多增益。商店按实时价格和刷新商品做选择，本次低价不代表静态规则的长期售价。

最后一手只剩一次出牌，用全部当前增益枚举，保留三红加三蓝的 218 分组合。尽管另有两张橙色武将，加入它们会占掉蓝品质和盾兵联动的位置，单张基础更高并不代表整手更高。

可改进之处集中在状态读取和计算校验：更早复用工具、明确已知修正、避免重复窗口诊断和无反馈等待。这轮 1267 证明构筑可通关，不证明其为随机牌库下的全局最优策略。
